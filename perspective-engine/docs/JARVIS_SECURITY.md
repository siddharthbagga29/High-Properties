# JARVIS security model (Perspective Engine)

Jarvis is a security-sensitive agent: it reads untrusted content, holds private memory and can act on a computer. This file lists the threats and the control for each. Controls marked **[built]** have tests; **[planned]** are designed but not yet implemented.

| # | Threat | Control |
|---|---|---|
| 1 | A visitor uses the public page to reach private data or actions | Viewer mode from `user.isOwner()`; visitor tools limited to `scope: public` and `riskLevel: safe` by `policy.decide`; private data stored under `data/users/<owner>/`, which the platform hides from everyone else; visitor writes refused by the page's access rules (checked with `as_level` on the live artifact). **[built and tested: core policy tests, city isolation tests, live access-rule check]** |
| 2 | Prompt injection in a web page, document, email, search result or agent output | Trust labels (`system > user > application > memory > tool > external`); untrusted content wrapped as data with a standing rule; instruction-like text flagged; tools never invoked because content asked. **[built in core]** |
| 3 | Over-autonomy | Risk levels 0–3 with confirmation at 2 and 3; level 3 cannot be pre-approved; denied list; audit entry for every decision. **[built in core]** |
| 4 | Secrets leaking into memory, prompts or logs | `redact()` on every audit summary and memory write; memory refuses credential-like text; no secrets in the database. **[built in core]** |
| 5 | Remote control of the Mac | Mac agent binds 127.0.0.1 only and refuses another host (`server.ts` `assertLoopback`); bearer token compared in constant time (`auth.ts`, `timingSafeEqual`); Host and Origin checks against DNS rebinding; CORS limited to its own console. **[built in `jarvis/agent`; tested with a real server on a random port; not yet run on a real Mac]** |
| 6 | Path traversal / arbitrary file access | File tools resolve real paths (`fsguard.ts`, `realpathSync`, nearest existing parent for new files) and refuse anything outside the allowlisted roots; symlinks resolved before the check. **[built; traversal and symlink-escape tests]** |
| 7 | Command injection | No shell: processes start with `spawn` and an argument vector, `shell: false` (`exec.ts`), from an allowlist of program and argument patterns (`tools/shell.ts`); destructive commands are level 3. **[built; metacharacter and allowlist tests]** |
| 8 | SSRF from browser or fetch tools | Agent-initiated fetches and browser navigation refuse private, loopback, link-local (including 169.254.169.254) addresses and non-http(s) schemes (`net.ts`); `open.url` only hands http(s) links to your own browser. **[built; SSRF tests]** |
| 9 | Runaway retries or loops | Bounded retries with exponential backoff, per-tool circuit breaker, timeouts. **[built in core]** |
| 10 | Fabricated progress | Tasks reach `completed` only with `verifiedBy`; status sentences are computed from task data; `graph.py done` refuses unless, after the task's last change, the latest verifier check ends `VERDICT: PASS` and the outputs are byte-identical to what that check saw (hashes recorded with the check); the auditor replays the ledger and flags any status that graph.json shows but the ledger does not explain. Limit: `--verifier` is a flag, not an identity, so separation of duties is procedural (a separate agent) and is checked by the independent LLM auditors. **[built + auditor; 51 tool tests]** |
| 11 | Fake revenue, gate clearances or unblocks (an agent acting as the founder) | Founder actions are signed with the founder's SSH key once it is registered (`graph.py founder-key`). The key is recorded in the ledger, which is append-only: the auditor checks every committed version against the next in git history, and `graph.py` treats a key that ever appeared in git history as registered, so deleting the line fails closed. A later key comes into force only if the previous key signed it; fingerprints are recomputed from the keys. Each action is signed over one JSON line (action, fields, sha256 of the record at that moment; for clear-gate also the output hashes the founder is approving), so a signature cannot be moved to another action, smuggle extra fields or be replayed once the record moves on. The face forms only from revenue whose signature the export re-verified (`sigVerified`), so with no key registered it cannot form at all. The auditor, independently of graph.py, re-verifies every signature, flags unbacked signed rows, reused signatures, gates cleared without a ledger event and statuses graph.py did not set. Tested with real ssh-keygen signatures, including every bypass two independent reviews demonstrated (`tools/test_founder_auth.py`). **[built; needs the founder to register a key]** Residual risks, stated plainly: the ledger is a file agents can write, so these controls detect tampering (git history, auditor) rather than prevent it; the first registration is trust on first use (confirm the fingerprint); before registration founder actions are attested only; two byte-identical copies of the record accept the same signature; an agent able to edit graph.py, audit.py and git history together could defeat them, which the remote repository's history would show. |
| 12 | Covert visitor surveillance | Session-only, in-memory interaction signals (dwell, repeated clicks, back-and-forth, Help); no keystrokes, form contents, audio, clipboard or identifiers stored or sent; a privacy line in Help. **[built in the city; visitor tests]** |

Reporting: anything that looks like a security issue is logged as an audit finding with severity `critical` and raised to the founder in the next briefing.
